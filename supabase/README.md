# Dedicated PD3 administrator backend

The `/studio/reviews` browser UI connects to a dedicated Supabase staging project using a publishable key. Authorization is enforced by PostgreSQL grants/RLS and private Storage policies. Vercel Authentication remains enabled on the entire staging frontend. Ordinary players do not need accounts.

## Deployment status and setup boundary

The dedicated PD3 staging backend has been provisioned in the user-approved organization on the Free plan in Seoul. The schema and private bucket are installed. Managed PostgreSQL checks passed all 14 permission assertions, and every synthetic fixture was rolled back. Security advisors reported no findings. The migration file was created using Supabase CLI 3.4.0. Apply it only to the dedicated PD3 staging project after confirming its ID/name and healthy status and inspecting its tables. Do not apply it to another application's database. Run Supabase security/performance advisors after installation and verify that anonymous and unregistered identities cannot read tables/images.

## Administrator bootstrap

Create the initial account in the dedicated project's Auth dashboard, with the user's chosen email and a password set through that dashboard. Do not put passwords in this repository or the chat. Configure administrator-only account creation in the Auth settings; there is no signup form in the player or Studio.

After verifying the intended Auth user ID and confirmed identity, a trusted database operator can grant membership:

```sql
-- Replace this UUID only after confirming the intended account in Auth.
insert into public.pd3_members(user_id,role,active)
select id,'owner',true from auth.users
where id='00000000-0000-0000-0000-000000000000'::uuid
  and email_confirmed_at is not null;
```

Only the database operator provisions membership. Browser identities and the validation worker cannot self-grant roles. Membership management through the web is outside this increment. Revoke access by setting the matching `pd3_members.active` to false; every new query checks this table, independently of stale JWT profile metadata. Auth signout clears the local session and refresh credentials; existing access tokens follow the provider's expiry rules. Deactivating membership is the immediate authorization revocation mechanism.

## Frontend connection

The private build copies `PD3-assets/qa/admin-config.json` to the protected frontend only after validating its shape:

```json
{
  "url": "https://YOUR_PROJECT_REF.supabase.co",
  "publishableKey": "sb_publishable_REPLACE_WITH_PUBLISHABLE_KEY"
}
```

Use a modern publishable key. Secret/service keys are rejected by the client and private build. Without this configuration the page displays “서버 연결 준비 중” and offers the working local editor. It never pretends to have authenticated against a live server. The publishable config grants no database or file access on its own.

## Data and permissions

- `pd3_members`: active editor/reviewer/owner roles; users can read their own membership, with no browser writes.
- `pd3_review_requests`: content-bound immutable metadata, creator identity and upload state. Editors see their own rows; reviewers/owners see the queue. Only the creator can finish a partial upload.
- `pd3_review_validations`: immutable independent image-check receipts; only the trusted server worker can insert them.
- `pd3_review_decisions`: immutable approval/rejection, authenticated actor ID, note and timestamp. Approval requires a completed upload and a passed independent check. Reviewers/owners can reject a completed request before the check finishes.
- `pd3-review-images`: private bucket with two exact image paths per revision, 16MB per image and PNG/WebP MIME types. No browser replace/delete policy exists. Downloads use the authenticated Storage API, followed by image hash/dimension checks. No public/signed image links are generated by this UI.

SQL verifies canonical content/digests, bounded metadata and image paths, upload completion, identity and role. A privileged worker re-decodes actual image bytes and checks geometry, transparency and changed-pixel coverage. Browser readiness claims never substitute for this check. Failed network transfers stay retryable; real content/byte failures receive a failed receipt. Edits require a new content revision. The inbox displays the latest 50 visible requests.

## Trusted validation worker

Install the existing Python image requirements and Node dependencies. Set these values only in the trusted worker environment:

```text
PD3_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
PD3_SUPABASE_SECRET_KEY=sb_secret_...
PD3_PYTHON=path-to-python-with-Pillow-and-numpy
```

Run `node scripts/validate-inbox.mjs`. It reads up to 10 completed unchecked requests, privately downloads images, reconstructs the review package and calls the independent Python validator. It records pass/fail receipts without approving content. Temporary package files are cleaned after each check. It never changes roles, decisions, the game catalog or a deployment. The secret key must never be placed in frontend config, NEXT_PUBLIC variables, Git or chat. Connecting/running this worker with a live secret is a separate setup step; no secret is provisioned by the browser.

Web decisions do not yet automatically feed the offline catalog/deployment pipeline. The existing explicit private selection, build, QA and protected staging deployment remain required. Public release and paid services still require separate approval.

## Approved server review export

`node scripts/export-approved-review.mjs DIGEST PRIVATE_OUTPUT.json` uses the trusted worker URL/key environment to fetch one completed, independently checked, approved revision. It downloads both private images, verifies metadata/digests, runs the real Python pixel validator again, and rereads server approval metadata before writing. The export is atomically linked to an unused output path outside this source checkout; existing files are never overwritten. Choose a private destination outside every public checkout.

The private envelope preserves the source project, authenticated decision actor/note/timestamp, worker receipt and content-bound Studio package. It is an unsigned snapshot taken by a trusted operator, not a portable authorization token. Editing a downloaded JSON cannot confer server authority. The contained package can be imported into Studio for fresh QA/test play, or submitted to the local review vault as **pending**. The existing catalog requires a separate trusted local decision; this exporter never fabricates `trusted-local-operator` authority, writes a decision, activates a catalog or deploys a website. Hosted approval-to-catalog authority transfer remains a separate step.

Missing/rejected/pending/failed or ambiguous approval records fail closed. Altered bytes, outside-region changes, transfer failures and an approval change during download leave no output. Exported files contain private images and answers: never put them in public Git, browser build output, public artifacts or chat. Only explicitly selected digests are exported; there is no automatic bulk download.

Export tests cover both object and single-element array relationship shapes returned by server adapters. Neither shape changes the approval requirements.
